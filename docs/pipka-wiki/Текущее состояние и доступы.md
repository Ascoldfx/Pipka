## Рабочая логика

### Сканирование и очереди

- План поиска формируется отдельно на пользователя из его `target_titles` и `preferred_countries`; вакансии дедуплицируются в общей таблице.
- Пользователи обрабатываются round-robin. Внутри очереди первыми идут более свежие вакансии; embedding similarity только меняет приоритет в ограниченном свежем окне и не отсекает кандидатов.
- Обычный скан — раз в 60 минут. Backfill — раз в 2 часа; scope на пользователя: его страны, вакансии не старше 31 дня, active/unknown URL и новые для профиля вакансии либо прежний score не ниже 60.
- Жёсткие pre-filter отказы получают `score=0` без вызова AI. Tier 1 (Director/Head/VP + domain) раньше Tier 2.
- Embeddings: NVIDIA `nvidia/nemotron-3-embed-1b`, размерность 2048. Обычный индексатор — раз в 2 часа, пакет до 70. Burst — раз в 30 минут при scoped queue строго больше 100.

### AI scoring

- Основной scorer: Gemini `gemini-3.6-flash`; production cap — 20 запросов в сутки, persistent учёт через Ops events. В момент аудита дневная квота была исчерпана, breaker ожидал сброса в 08:00 UTC.
- Автоматический fallback: NVIDIA `poolside/laguna-xs-2.1`. Streaming включён; одна вакансия за запрос, timeout 60 секунд, одна попытка, max output 768 токенов. Это минимизирует блокировку очереди.
- Проверка на реальном полном prompt: одна вакансия получила валидную оценку за ~20 секунд в streaming режиме; обычный проход записал новые NVIDIA scores. Доступность не абсолютная: наблюдались timeout и HTTP 503.
- Детальный Gemini-анализ отключён по умолчанию, чтобы он не конкурировал с batch scoring за дневную квоту.
- Embeddings идут через отдельный endpoint NVIDIA и не используют модель чата scoring.

### Ops и security-probes

- Из ленты Ops исключаются известные чужие probe paths (`/api/templates/preview`, `/api/fs/exec`, `/api/graphql`, `/api/inngest`, `/api/designer/v1/file-content`, `/api/v1/validate/code`) только для unsafe HTTP-методов и ответов 403/404.
- Запросы по-прежнему отклоняются middleware и доступны в access logs. Исторические Ops события не удаляются.
- Настоящие ошибки API и ошибки CSRF на рабочих Pipka endpoints продолжают попадать в Ops.

## Доступы и границы пользователей

### Сервер

- Host: `217.76.61.28`, deployment user: `pipkaops`, приложение: `/opt/pipka`.
- SSH key login из локального окружения: `~/.ssh/id_ed25519`; администрирование через `sudo`. Секретный материал приватного ключа в заметках не хранить.
- Production `/opt/pipka/.env`: режим `0600`, владелец `root:root` (проверено без чтения содержимого).
- Root/password SSH login ранее закрыты hardening-конфигурацией; это состояние не перепроверялось в рамках данного снимка.

### Вход в приложение и роли

- Google OAuth настроен. Учетная запись и роль берутся из БД; защищённые admin routes должны использовать DB-backed `require_admin_async` (TTL 60 секунд), не косметическую роль из session cookie.
- На момент аудита `ALLOW_PUBLIC_REGISTRATION` отсутствовал в production `.env`, а default в коде — `true`. Значит, public registration фактически включена. `ALLOWED_USER_EMAILS` и `ALLOWED_TELEGRAM_IDS` в env не заданы.
- `DASHBOARD_USERNAME`, `DASHBOARD_PASSWORD`, `GUEST_USERNAME`, `GUEST_PASSWORD` существуют в production env, но по текущему коду не используются; в проверенных nginx-конфигах `auth_basic` не найден. Не считать их действующим дополнительным барьером.
- Веб-сессия подписана `SESSION_SECRET`, cookie защищена HTTPS/SameSite. Unsafe методы защищены CSRF. Не передавайте session cookie между клиентами.
- Данные вакансий общие; профили, оценки (`job_scores`), отклики (`applications`) и настройки должны фильтроваться по текущему `user_id`. Изоляция обеспечивается API/ORM-слоем; PostgreSQL RLS не включён.
