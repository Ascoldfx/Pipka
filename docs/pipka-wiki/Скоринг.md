# Скоринг вакансий

Двухэтапная система: сначала быстрый rule-based фильтр, потом дорогой AI.

## Этап 1: pre_filter() — без AI

Файл: `app/scoring/rules.py`

### Жёсткие отказы (return False)
| Проверка | Причина |
|----------|---------|
| Title содержит junior/trainee/analyst/specialist/coordinator… | Слишком низкий уровень |
| Title содержит marketing/sales/HR/engineering/software/product… | Не та функция |
| Описание требует французский/испанский/польский | Кандидат не владеет |
| `excluded_keywords` из профиля пользователя | Персональные исключения |
| `english_only=True` + нет English-friendly сигналов | Только английские вакансии |
| Нет доменных слов: supply chain/procurement/operations/logistics… | Не та область |
| `plain manager` (без Director/Head/VP/Lead) + нет domain | Слишком низкий уровень |

### Бакеты
| Бакет | Условие | Идёт на AI? | Когда |
|-------|---------|-------------|-------|
| `high` | Director / VP / Head / COO / CRO / Chief + domain | ✅ | Tier 1 (приоритет) |
| `medium` | Senior Manager / Lead + domain | ✅ | Tier 1 (приоритет) |
| `manager_tier2` | Plain manager + domain (supply chain manager, ops manager…) | ✅ | Tier 2 (после Tier 1) |
| `low` | Всё остальное — junior, не та функция, иностранный язык | ❌ | Никогда (score=0 сразу) |

### Расширенные ключи для `high` бакета (22.04.2026)

Помимо стандартных Director / VP / Head / Chief / C-suite, в `DIRECTOR_KEYWORDS` также:

- **Interim / Crisis / Turnaround:** `interim manager/director/head`, `crisis manager/director`, `krisenmanager` (DE), `turnaround manager/director`, `restructuring`
- **Growth:** `growth director`
- **C-suite расширен:** добавлен `cro` (Chief Restructuring / Revenue Officer)

В `DOMAIN_KEYWORDS` для таких ролей добавлены: `crisis management`, `turnaround`, `transformation`, `restructuring`, `interim management`, `business continuity`, `operational excellence`, `continuous improvement`, `growth`.

## Этап 1.5 (опционально): semantic pre-rank

`?semantic=1` в `/api/jobs` использует cosine-similarity между embeddings для UI retrieval. В scheduler та же similarity используется только для порядка AI-очереди: exact target → similarity выше threshold → без embedding → similarity ниже threshold. Ни одна вакансия не удаляется; `semantic_skip` упразднён migration `0008`.

Подробнее об индексации и self-управлении кэшем embeddings — [[Поиск и индексация]].

## Этап 2: AI скоринг

### Распределение backend'ов (сверено 23.09.2026)

| Операция | Backend | Почему |
|---------|---------|--------|
| `_score_and_notify` (реальное время, push в Telegram) | **Gemini 3.6 Flash** если `GEMINI_API_KEY` задан и breaker закрыт; иначе **NVIDIA** | При квоте Gemini или открытом breaker новый скоринг переходит на NVIDIA; ошибки провайдера всё равно возможны. |
| `_backfill_score` (каждые 2ч, cap на пользователя) | **Gemini 3.6 Flash** или **NVIDIA** как fallback | Отдельная пользовательская очередь: свежие вакансии и Tier 1 идут раньше Tier 2. |
| `analyze_single_job` (кнопка «AI-анализ») | **Gemini 3.6 Flash** или **NVIDIA** (fallback) | Детальный разбор вакансии по требованию. При выключенном детальном анализе Gemini переходит на NVIDIA. |
| `recheck_zero_scores` (перепроверка pre-filter rejects) | **Gemini 3.6 Flash** (только если есть квота) | Вторая проверка не обходит дневной лимит |

Google-интеграция переведена с лимитированного `google-generativeai` на `google-genai>=2,<3`. Скоринг и embeddings используют общий async client/pool.

### NVIDIA Build (автоматический fallback и отдельный idle rescorer)

Файл: `app/scoring/nvidia_matcher.py`. Production-модель: `poolside/laguna-xs-2.1`. NVIDIA используется как fallback скоринга, в частности при недоступности/исчерпании Gemini. Ответы обрабатываются потоково (SSE), по одной вакансии за запрос; это уменьшает размер и время запроса, но не гарантирует успех: зафиксированы timeout и HTTP 503. Текущие параметры production: batch size 1, timeout 60 секунд, одна попытка, максимум 768 output tokens.

Отдельный `_nvidia_idle_rescore` — необязательная задача переоценки; она запускается только при `NVIDIA_IDLE_RESCORE_ENABLED=true` и не является механизмом обычной очереди.

Опциональный job `_nvidia_idle_rescore` (каждые 30 мин) включается только через `NVIDIA_IDLE_RESCORE_ENABLED=true`; по умолчанию выключен. Per-user guard — запускается только если unscored queue для `country=de, ≤45 дней` равна **0**. Две фазы:

1. **Recheck rejects:** обновляет JobScore для пре-фильтром отклонённых (`score=0, ai_analysis IS NULL`).
2. **Refresh stale:** освежает старые оценки со `score > 0` и `scored_at < now - 7д` (параметр `nvidia_rescore_stale_days`).

Cap `nvidia_max_per_run=300` за тик. Pacer 2с + Semaphore(1) + tenacity retry на 429/5xx.

Fallback не блокирует очередь навсегда: отдельная вакансия может завершиться timeout/503 и потребовать следующего прохода. Следите за последними успешными попытками в [[Ops панель]] и за возрастом самого старого элемента очереди.

### Circuit breaker (25.04.2026)

`gemini_matcher.py` ведёт счётчик подряд-exhausted батчей. При **3** подряд или немедленно при 429/исчерпанном `GEMINI_DAILY_REQUEST_LIMIT` → `_gemini_disabled_until = next reset time` (08:00 UTC, согласовано с полночью в Калифорнии). `is_gemini_available()` гасит scorer-вызовы, после сброса breaker сам возвращается в норму. OpsEvent: `gemini_breaker_open` (severity=warning).

Брейкер влияет на real-time push (`_score_and_notify`), `recheck_zero_scores` и backfill. При исчерпании лимита Gemini real-time скоринг автоматически переходит на NVIDIA fallback, чтобы новые вакансии не оставались без оценки.

### Надёжность вызовов (Фаза 1, 24.04.2026)

`app/scoring/gemini_matcher.py` обёрнут:

- **`tenacity` retry** — 5 попыток, exp backoff 5→10→20→40→80с + ±2с jitter только для 408/5xx и timeout-классов. `429/ResourceExhausted` не повторяются.
- **`asyncio.Semaphore(1)`** — один in-flight запрос на процесс.
- **Global pacer** — минимум `GEMINI_BATCH_DELAY` между scorer-вызовами.
- Каждая попытка заранее записывается как `OpsEvent("gemini_request", "attempt")`; это persistent RPD-счётчик, переживающий рестарт. 429 → один `gemini_429/error` и breaker до полуночи.
- Batch-ответ задаётся JSON Schema; markdown-strip/truncated-JSON repair оставлены только как defensive fallback.

### 2a. NVIDIA (fallback — когда Gemini не настроен, breaker открыт или лимиты превышены)

Файл: `app/scoring/nvidia_matcher.py`

- Потоковый режим: **1 вакансия** за запрос в production; общий batching fallback не используется.
- **Лимит времени в real-time пути:** внутри часового скана NVIDIA-оценка ограничена `NVIDIA_REALTIME_MAX_SECONDS=300`. До 23.09.2026 деградировавший NVIDIA (15 вакансий × 120 с таймаута) растягивал скан до 32 минут и блокировал следующий.
- **Устойчивый разбор ответа:** берётся первый JSON-значение ответа (массив или одиночный объект), хвостовой комментарий модели игнорируется; ремонт обрезанного массива — запасной путь. Раньше `Extra data` после массива выбрасывал всю оценку.
- Лимит за скан: проверяйте актуальный cap в конфигурации `_score_and_notify`; он не равен размеру запроса к NVIDIA.
- Кэш: **7 дней** (`score_cache_hours=168`) — не переоцениваем одно и то же
- Модель production: `poolside/laguna-xs-2.1` (настраивается через `NVIDIA_MODEL`)
- Используется в: **fallback** для `_score_and_notify()` и `_backfill_score()` — когда Gemini исчерпан или выключен.

### 2b. Gemini 3.6

Файл: `app/scoring/gemini_matcher.py`

- Активируется: если в `.env` задан `GEMINI_API_KEY`
- Скоринг: `gemini-3.6-flash` (`GEMINI_SCORING_MODEL`), по 15 вакансий в одном запросе
- Дефолтный лимит: 20 запросов за UTC-день (`GEMINI_DAILY_REQUEST_LIMIT`) = до 300 вакансий в сутки при полном батче
- Детальный анализ выключен через `GEMINI_DETAILED_ANALYSIS_ENABLED=false`, чтобы не отнимать этот лимит
- Используется в: `_score_and_notify()`, `_backfill_score()` и `recheck_zero_scores()`
- Для 3.5/3.6 намеренно не передаются deprecated `temperature`, `top_p`, `top_k`
- Зарплата не включается в job context и не может влиять на score/verdict
- Получение ключа: [aistudio.google.com/apikey](https://aistudio.google.com/apikey)

## Backfill scorer

Проблема: основной сканер скорит только вакансии из текущего скана. Если в базе уже тысячи вакансий — большинство остаются без оценки.

Решение: `_backfill_score()` каждые **2 часа** строит отдельную виртуальную очередь для каждого user. Страны берутся из его `preferred_countries`; вакансии не старше `backfill_max_age_days=31`, active/unknown, с прежним score ≥ `backfill_min_previous_score=60` или ещё без score для этого user. После изменения профиля слабый старый архив не возвращается. Пользователи идут round-robin, по **15 самых свежих кандидатов** на user за проход.
- `low` bucket → `JobScore(score=0)` мгновенно, без AI-вызовов (дренаж персональной очереди)
- `high`/`medium` → AI-скоринг (Tier 1)
- `manager_tier2` → AI-скоринг (Tier 2, только когда Tier 1 пуст)

**Бюджет прогона зависит от бэкенда** (с 23.09.2026, `_backfill_budget`):

| Бэкенд | Вакансий на user за прогон | Почему |
|---|---|---|
| Gemini (breaker закрыт) | `min(MAX_JOBS_PER_SCORING_BATCH, BACKFILL_AI_JOBS_PER_RUN)` = **15** | Одна пачка = один запрос из дневной квоты `GEMINI_DAILY_REQUEST_LIMIT=20` |
| NVIDIA (нет ключа Gemini или breaker открыт) | `NVIDIA_BACKFILL_JOBS_PER_RUN` = **120** | NVIDIA — 1 вакансия/запрос (~10–15 с), отдельная квота. При бюджете 15 он простаивал ~117 минут из 120, и бэклог не мог рассосаться (макс. 180 оценок/сутки при спросе ~370) |

В режиме NVIDIA действует общий лимит времени прогона `NVIDIA_BACKFILL_MAX_SECONDS=2700` (45 мин); он проверяется **перед каждым запросом** к NVIDIA (перебор — не больше одного зависшего запроса, ≤2 мин) — прогон гарантированно заканчивается до следующего 2ч-тика; каждая оценка коммитится сразу, недооценённое ждёт следующего прогона. Если Tier 1 исчерпан внутри прогона, остаток бюджета сразу уходит на Tier 2.

**AI backend для backfill:** Gemini 3.6, если задан ключ и доступна квота; иначе NVIDIA. При исчерпанном лимите Gemini фоновый скоринг переключается на NVIDIA, постепенно закрывая всю очередь.

NVIDIA fallback обрабатывает одну вакансию за запрос, с timeout 60 секунд, одной попыткой и пределом 768 output tokens в текущей production-конфигурации. Параметры задаются через `NVIDIA_SCORING_BATCH_SIZE`, `NVIDIA_SCORING_TIMEOUT_SECONDS`, `NVIDIA_SCORING_MAX_ATTEMPTS` и `NVIDIA_SCORING_MAX_TOKENS`. Gemini сохраняет собственную пакетную обработку; это независимые пути.
